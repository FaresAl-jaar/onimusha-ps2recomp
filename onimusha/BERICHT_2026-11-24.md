# Stand 24.11.2026: Videos und ADX Musikneustart

## Videos (erledigt, auf main)

Sofdec Videos spielt jetzt der Host mit FFmpeg ab (`ps2xRuntime/src/lib/games/onimusha_dod_movies.cpp`). Vorbild ist der Soulcalibur III Port von TheBozos.

* **Was ersetzt wird:** Die Sofdec Hülle des Spiels mit Start (0x2b01c0), Stopp (0x2b0370), Bild (0x2b03c0), Bild freigeben (0x2b0440) und Status (0x2b0470).
* **Bild:** Es geht als RGBA32 Makroblöcke an das Spiel, spaltenweise angeordnet wie bei Sofdec, Alpha 0x40.
* **Ton:** Der ADX Ton wird in die Host Audioausgabe gemischt.
* **Getestet:**
  * Intro komplett (3873 Bilder) mit Ton und Untertiteln
  * Überspringen mit Start
  * Mehrfaches Starten hintereinander: Intro, nach New Game wieder 66, dann 67_US
* **Abschalten:** `PS2X_NATIVE_MOVIES=0` nutzt wieder den Sofdec Player des Spiels.

## Offener Hänger: ADX Musikneustart

Nach New Game bleibt der Bildschirm schwarz, das Spiel läuft aber weiter.

**Messung mit `PS2X_ADXT_LOG=1`:** Der Musikstrom `0x4bef88` startet beim ersten Mal sauber (Status 0, 1, 2, 3). Nach Stopp und Neustart bleibt er in PREP (2). Es ist derselbe Fehler, der vorher das zweite Video blockiert hat.

**Ursache, soweit bekannt:**
* Die RNA Ausführung auf dem EE (0x24f4a0) wartet bei gesetztem Reset Flag (+0x58), bis jeder Kanal SJ komplett frei ist.
* 2048 Byte (1024 Samples) bleiben liegen, weil die IOP Seite sie nie abholt.
* SPU2 AutoDMA auf Core 1 läuft während Stopp und Neustart normal weiter.

### Geprüfte Fehlerklassen anderer Projekte

* **TheBozos `9dc213a`** (Branch main, 26.10.2026): Ein Inline RPC Aufruf wartet auf die Threads, die den Server Thread überholen.
  * Bei uns nicht einzeln übertragbar, weil unser IOP RPC Server als reinen Funktionsaufruf (`callFunction`) ausführt, nicht als Thread.
* **TheBozos `e749e57`:** Liegt nur auf dem Branch `sc3/native` und betrifft den Modus „SPU2 auf Wanduhr“, den wir nicht nutzen.
* **BT3 (nicht rekursiver Mutex über `iopImport`):** Den `iopImport` Pfad gibt es bei uns nicht, der Aufruf Lock (`CallScope`) ist rekursiv.

### A/B Test

* **A** (main): Musikneustart hängt in PREP, reproduzierbar.
* **B** (Branch `iop-bozos`): Das komplette ps2xIOP von TheBozos main, das `9dc213a` enthält.
  * Der Build ist fehlerfrei, das Spiel bootet aber nicht.
  * Grund: Der Soundtreiber SNDDRV bindet einen IOP → EE RPC Server (`sid 0x77777779`). Dieser IOP wartet auf einen echten EE Server. Unsere Runtime liefert den noch nicht (`IopHost::findEeRpcServer`, `callEeRpc`).
  * Damit sind die Prüfpunkte für B noch offen: ob die 2048 Byte verbraucht werden, PREP auf PLAY wechselt und New Game ins Gameplay kommt.

### Nächste Schritte (zur Entscheidung)

1. **B weiterführen:** IOP → EE RPC in unserer Runtime nachbauen (EE Server Register und Aufruf über `sceSifRpcLoop`), dann B messen und die verantwortliche Änderung eingrenzen.
2. **Alternative:** Nur die Thread Ausführung von RPC Servern gezielt in unseren IOP übernehmen. Das ist kleiner, aber ohne den Rest der TheBozos Fixes.

## Nachtrag: Musikneustart behoben

**Messpunkt korrigiert:** Das RNA Objekt eines ADXT Handles liegt bei `handle+0x0c`, für `0x4bef88` ist das `0x4d9930` (Kapazität 0x4000, 2 Kanäle). Beim Hänger waren pro Kanal nur 0x3400 von 0x4000 Byte frei. 0xC00 Byte steckten in Chunks zu 0x400 und kamen nie zurück. Die Flags blieben auf `0x01010101`.

**Einzeln getestet am selben Ablauf (`/tmp/padS.txt`):**
* **Änderung 1** (Prinzip TheBozos `9dc213a`, vor einem Inline RPC laufen die bereiten IOP Threads mit gleicher oder höherer Priorität), `boot150`:
  * greift, ändert am Hänger aber nichts
  * jetzt standardmäßig aus, `PS2X_IOP_RPC_AHEAD=1` schaltet sie ein
* **Änderung 2** (Interrupts und Threadwechsel ruhen, solange `CpuSuspendIntr` aktiv ist; gleiche Fehlerklasse wie TheBozos `64181c7`), `boot151`, `boot152`, `boot153`:
  * Der zweite Start von `0x4bef88` geht 0, 1, 2, 3 (PLAY), danach 4, 5, 0.
  * Danach laufen weitere Ströme an (`0x4bf050`, `0x4bf2a8`).
  * New Game erreicht Stage 1 „Dawn of Nightmares“ und das Spielmenü.
  * `PS2X_IOP_INTR_MASK=0` schaltet sie zum Vergleich ab.

**Ursache:** Unser IOP stellte Interrupts zu und wechselte Threads, auch wenn ein CRI Thread gerade eine SJ Chunk Liste unter gesperrten Interrupts bearbeitete. Dabei gingen Chunks verloren.

**Vergleichsstand:** Tag `stand-vor-intr-fix` (Commit 105ba68).

**Nächster Blocker:** Die 3D Spielszene bleibt schwarz (Bildwerte 0), Menüs und 2D werden gezeichnet.

**Noch offen:**
* Regressionstest von Videos, Dialogen, Effekten und Controller
* mehrfacher Musikwechsel im Spiel
